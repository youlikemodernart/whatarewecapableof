PiOp Minimal is a portable, curated setup for Pi, the agent runtime.[1] It gives a recipient a dependable way to use Pi for real work across files, terminal, public web, models, skills, and delegation while keeping authority, privacy, and recovery explicit. "Minimal" describes the delivery model: ordinary Pi packages, portable files, a Recipient Profile, and a small bootstrap, rather than a custom installer.[2]

PiOp tracks which capabilities are present, what it must ask before acting, where work belongs, and how to leave a recovery path. An installation adds only what a reviewed plan approves; the product explains what an installation can include and prepares a reviewed request.

Overview [edit]

A capable Pi setup accumulates useful operating behavior across instructions, skills, extensions, helper tools, profiles, model access, and recovery knowledge. Without a product layer, that setup is hard to transfer and support. PiOp turns the accepted parts into one understandable, recipient-ready product with one source of truth.[2]

PiOp distinguishes several capability states. Known, installed, configured, authenticated, available, verified, and ready describe different conditions: a supported tool can be known without being installed, and installed without being ready.

Product shape [edit]

PiOp holds three distinctions that are often collapsed.

IS Terminal [edit]

IS is the recommended macOS terminal and persistent workspace host for PiOp. Pi remains the agent runtime; PiOp supplies the curated operating setup; IS supplies the native place where terminal sessions, panes, and visible agent workspaces live.[3]

IS, Pi, and PiOp
LayerRoleBoundary
ISNative macOS terminal, window, tab, pane, and workspace host.It does not replace Pi or decide what an agent may do.
PiAgent runtime that reasons, uses tools, and carries out approved work.Its model, tools, skills, and authority remain separately configured.
PiOpPortable setup that supplies operating behavior, selected capabilities, recipient context, and explicit boundaries.It works in an ordinary terminal; IS is recommended rather than required.

What IS provides

Native terminal foundation
A Swift and Metal terminal with PTY and VT handling, scrollback, selection, mouse support, inline images, tabs, nested splits, and a quick terminal.
Persistent workspaces
Optional workspace restoration rebuilds native windows, tab groups, split geometry, names, focus, and working directories. Optional tmux backing keeps shell and agent processes alive through an app restart.
Visible agent work
Agent Workspace can create named, resumable Pi and Claude workspaces in IS. Restored panes retain bounded lineage so the controller can verify the intended workspace before resuming it.
Guarded control
A bounded local control layer can inspect panes and perform explicitly approved writes without treating terminal reach as standing authority. Read, write, focus, launch, restart, and replacement remain separate effects.
Shell semantics
Shell integration uses command markers to identify prompts, input, output, completion, and exit status without relying only on screen scraping.
Recipient-controlled appearance
Configuration covers fonts, type size, spacing, margins, colors, window chrome, opacity, quick-terminal behavior, working-directory policy, and interface scaling.
Pane-safe interaction
Keyboard selection identifies the intended terminal pane for contextual Copy, Paste, and Reset actions. The selected pane receives a visible outline while its context menu is open.
Pinned updates
IS does not silently replace itself. Release, download, installation, app replacement, restart, rollback, and update-channel activation remain explicit lifecycle steps.

Skills add focused methods for particular kinds of work. PiOp selects them from its accepted capability graph according to a recipient's use case. A selected root skill brings its declared required closures and bounded runtime resources into that recipient's bundle.

Delivery [edit]

The accepted PiOp source and skill graph govern what can enter a recipient bundle.[2] Recipient delivery is separate.

  • The recipient describes the outcome, working context, and relevant constraints.
  • The smallest useful skill set, required closures, scope, and risk are reviewed before fulfillment.
  • On approval, a recipient-specific ZIP is shared through private Google Drive.
  • The delivery email carries the exact copy-and-paste Pi setup prompt.

Boundary: A GitHub account is not required for delivery. Sends, deployments, credentials, and account changes keep their own approval boundaries.
