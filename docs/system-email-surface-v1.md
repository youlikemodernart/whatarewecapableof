# System Email Surface v1

Status: v1 core, v1.1 tables, aspect-aware v1.2.1 single figures, bounded v1.3 two-figure sequences, and v1.4 inline highlights are approved for current WAWCO use; opaque PNG is the production default and transparent artwork remains contrast-dependent
Last local verification: 2026-07-26
Implementation: `scripts/gmail-draft-markdown.mjs`, `scripts/gmail-draft-mime.mjs`, `scripts/gmail-draft-preview.mjs`, `scripts/gmail-draft-send.mjs`, and `scripts/gmail-draft.mjs`

## Purpose

System Email Surface v1 is WAWCO's default presentation for structured agent-authored email. It keeps Markdown as the authoring source and emits a deliberate HTML alternative plus a useful plain-text alternative.

The Email Rendering Baseline is the fixed technical layer beneath the surface. It owns MIME serialization, sanitization, compatibility markup, private previews, attachment validation, message-size checks, and the reviewed-payload approval gate. Presentation choices cannot bypass those controls.

## Authoring contract

Use `--body-markdown-file` for structured email. The v1 renderer supports:

- headings;
- paragraphs and explicit line breaks;
- ordered and unordered lists, including nested lists;
- bold and italic emphasis;
- bounded inline highlights using `==text==`, with `=={hot-pink}text==` reserved for rare special emphasis;
- inline code and fenced code blocks;
- blockquotes;
- horizontal rules;
- HTTPS, HTTP, and mailto links;
- up to two small data tables, each limited to three columns, twenty body rows, and 500 characters per cell.

The renderer rejects:

- raw HTML;
- embedded Markdown images outside the explicit bounded figure inputs;
- relative and in-document fragment links;
- JavaScript, data, file, and other unapproved URL schemes.

Remote images, galleries, side-by-side image layouts, styled attachment cards, PDF previews, fetched resource cards, and media thumbnails remain outside the current v1 family. Author-supplied resources may use the ordinary Markdown resource-list pattern below. A normal PDF may be attached through the helper and appears through each mail client's native attachment interface.

## Fixed presentation

The accepted WAWCO presentation is the closed `wawco.email.house` organization-expression profile at `email-expression/profiles/wawco/profile.json`. The production WAWCO Markdown path loads and validates that exact accepted profile, resolves its closed presentation values through `scripts/email-expression-resolver.mjs`, and passes them into the existing renderer. The legacy presentation object remains the no-argument renderer default and rollback reference. The profile does not expose arbitrary CSS, profile inheritance, automatic client selection, or client access to WAWCO's private expression.

Sender/account policy is separately resolved through the closed profile table in `scripts/gmail-mail-profiles.mjs`. New helper-built MIME records the exact mail-profile ID, version, and canonical policy digest. Stored-MIME review binds those markers to the explicitly selected profile before issuing an approval token. Legacy messages without profile markers remain reviewable only through the prior closed sender-policy inference during the rollback window.

- Fluid presentation-table layout with an exact 640px maximum.
- Conditional 640px MSO wrapper for desktop Outlook.
- System sans-serif body type at 16px with 24px line height.
- System monospace type for inline and fenced code.
- Dark neutral text, restrained blue links, light gray rules and code surfaces.
- Inline email-safe styles. No scripts, stylesheets, web fonts, forms, animation, or remote assets.
- Semantic headings, lists, blockquotes, links, code, horizontal rules, and data-table headers remain present in the HTML alternative.
- Data tables use real `table`, `thead`, `tbody`, and `th scope="col"` markup with inline compatibility styles. Cells use compact horizontal padding and normal word boundaries; the header rule is one pixel.
- Blockquotes use a restrained two-pixel left rule.
- A v1.2 figure uses one locally supplied PNG, a deterministic CID, descriptive alt text, and an optional real text caption. V1.3 permits two such figures in one vertical sequence.

Heading levels 4 through 6 are accepted by the CommonMark parser and deliberately share the h3 visual treatment. Authors should normally use levels 1 through 3.

## MIME and policy behavior

The helper serializes with Nodemailer and uses CRLF line endings, RFC-safe encoded headers, quoted-printable text alternatives when needed, and multipart nesting generated by the serializer.

Every agent-authored draft automatically Bccs `noah@whatarewecapableof.com` unless Noah is already a visible or hidden recipient.

For the default `noah@whatarewecapableof.com` path:

- the quiet-editorial system note is appended;
- the current private signature snapshot is required;
- the snapshot must be a direct, non-symlink, mode-0600 regular file;
- signature markup is reduced to `div`, `span`, `a`, and `br` elements;
- only HTTPS and mailto signature links survive;
- only color, font family, font size, font weight, line height, and text decoration survive the signature style allowlist.

Other accounts do not receive the Noah system note or private signature. Plain inputs remain plain text; `--body-markdown-file` may use the same structured HTML/plain alternatives from another selected account. Suppressing the default Noah system note requires the exact flag `--system-note=none` and current-session approval for agent-authored client email.

Every helper-built MIME message carries internal v1 policy headers for the helper version, body format, system-note mode, signature status, inline-figure mode, mail-profile ID/version/policy digest, and a SHA-256 digest over the decoded text, HTML, inline figure, and attachment content. WAWCO house messages additionally carry expression-profile ID, version, and SHA-256 markers. Stored-MIME review requires those three markers to match the current accepted WAWCO profile before issuing an approval token. Final Gmail review requires those markers, recomputes the semantic digest from the stored raw MIME, and rejects manual or accidental content drift before emitting an approval token.

## Component model

The fixed rendering baseline and visual grammar remain shared across the v1 family. Tables, figures, and inline highlights are optional component capabilities rather than separate visual profiles.

### V1.4 inline highlights

V1.4 adds short inline text highlights through `==text==`. The approved default is sun yellow (`#FFE08A`) with explicit dark text (`#202124`). The only named alternative is hot pink through `=={hot-pink}text==`, reserved for rare special emphasis rather than ordinary hierarchy.

The final palette follows manual comparison in Gmail and Apple Mail light and dark modes. Sun yellow was the strongest overall compromise. Gmail dark mode subdues it but leaves it usable. Apple Mail dark mode changed the text treatment on several more saturated candidates and reduced their contrast. Hot pink remained useful as a narrow exception. Client-specific dark-mode hacks were rejected in favor of solid colors and graceful degradation.

The component contract is deliberately narrow:

- maximum twenty highlights per message and 240 characters per highlight;
- one line of literal text per highlight, with no raw HTML or nested Markdown;
- inline `background`, `color`, and minimal padding only;
- no gradient, image, border-radius dependency, animation, remote asset, or color-only meaning;
- plain-text alternatives retain the words and remove the highlight markers;
- unknown palette names and over-limit content fail closed;
- the message must remain understandable if a client removes or inverts the background.

Use the default for short figures or phrases that need review attention. Use hot pink only when a second, stronger emphasis carries a clear meaning. Do not combine additional colors or use highlighting as decoration. Longer callouts should use a separately reviewed table-cell component rather than an oversized inline highlight.

### V1.1 small data tables

Markdown pipe tables are enabled only for structured Markdown bodies. The renderer permits at most two tables, three columns, twenty body rows, and 500 characters per cell. Header cells receive `scope="col"`. The plain-text alternative emits pipe-delimited rows with a header separator. Tables carry no nested layouts, images, or arbitrary HTML.

The three-column limit is a mobile readability boundary. Table cells preserve normal word boundaries instead of breaking words anywhere. Content with four or more fields should use stacked key-value records built from ordinary bold labels and lists, for example one component heading followed by `Version`, `State`, and `Fallback` list items. This avoids fragile responsive-table CSS and remains readable when an email client ignores advanced styling.

### Resource-list authoring pattern

A short set of author-supplied links does not need a new renderer component. Use an ordinary section heading followed by a semantic Markdown list. Each item should contain a descriptive linked title and one sentence explaining the destination or its role:

```markdown
## Resources

- **[Working brief](https://example.com/brief)**  
  Scope, decisions, owners, and the next review gate.
- **[Approved source folder](https://example.com/sources)**  
  Current inputs and exports approved for project use.
```

Keep the list short, usually one to five items. Write link labels that remain meaningful outside visual context. Supply every URL directly from the approved source material. The helper does not fetch titles, descriptions, favicons, Open Graph data, thumbnails, redirects, or other remote metadata. Do not turn the entire item into one large linked region. This pattern uses the existing list, link, emphasis, and plain-text contracts, so it adds no MIME type, policy marker, network access, or client-specific layout.

### V1.2 single inline figure

One figure may be supplied through `--inline-image`, `--image-alt`, and optional `--image-caption`. The figure:

- requires a direct non-symlink `.png` file;
- must declare and match `image/png`, the PNG signature, complete CRC-valid chunk bounds, a valid IHDR field set, nonempty IDAT data, and a final IEND chunk;
- is limited to 2 MiB, 2400 pixels on either side, and 8 million pixels total;
- receives a deterministic content-derived CID and `Content-Disposition: inline`;
- requires one-line alt text of 1 to 300 characters;
- may use one real-text caption of at most 500 characters;
- degrades in plain text to an image-description line plus caption;
- is never upscaled;
- uses an aspect-ratio-aware display cap: 640px landscape, 520px square, 440px portrait, or 360px tall portrait;
- emits a numeric width plus CSS `height:auto` but omits the HTML height attribute so a blocked image does not reserve a large empty frame.

The local and final-review manifests expose intrinsic dimensions, display dimensions, sizing class, and whether PNG transparency is present. Opaque PNG is the production default. Named iOS Gmail and Apple Mail evidence showed that transparent light artwork blended into light-mode backgrounds, while transparent dark artwork remained visible in the tested light and dark states because the client backgrounds provided contrast. Transparency therefore remains technically supported and reported, but authoring must treat its contrast as client-background-dependent. Do not use transparent light artwork as a generally safe production pattern without a controlled contrasting backdrop and fresh named-client evidence. Decorative figures with empty alt text remain unsupported; the figure system is for content-bearing images.

With a figure, Nodemailer creates `multipart/related` around the HTML alternative and inline PNG. PDF attachments remain outside that related part under `multipart/mixed`. Final review requires the matching PNG MIME part and matching indexed `cid:` source. Remote, data-URI, missing, duplicate, and mismatched sources fail closed. The private browser preview substitutes local data URIs for visual inspection and adds an image-disabled structural simulation; outbound MIME retains each CID.

### V1.3 bounded two-figure sequence

A message may repeat `--inline-image` and `--image-alt` twice to create a vertical two-figure sequence. Captions are either omitted for both figures or supplied positionally once per image; use `--image-caption=` for an intentionally empty position.

The sequence contract is:

- maximum two distinct local PNG files;
- vertical document order only, with no side-by-side layout or gallery;
- one alt value and optional caption position per figure;
- unique deterministic CIDs that include sequence position;
- indexed HTML figure and caption markers;
- the same per-image byte, dimension, pixel, filename, and accessibility limits as v1.2;
- preserved order in HTML, plain text, MIME related parts, semantic hashing, preview substitution, and final review;
- a `sequence-2-cid-png` policy marker;
- exact MIME topology `multipart/related(text/html, image/png, image/png)` inside the HTML alternative, with PDFs remaining outer mixed siblings.

Duplicate image bytes, a third figure, missing positional alt text, partial caption arrays, duplicate CIDs, reordered or mismatched HTML markers, and unsupported MIME trees fail closed.

## PDF attachment contract

Each attachment must:

- be supplied as a direct non-symlink file with a `.pdf` extension at the CLI boundary;
- declare `application/pdf`;
- begin with the PDF file signature `%PDF-`;
- stay within the 20-file count limit and 20 MiB aggregate source-attachment limit.

The message model copies attachment bytes before asynchronous serialization. Its local summary records the basename, MIME type, source bytes, and SHA-256 digest. Final Gmail review decodes the stored MIME attachments, repeats the PDF signature and policy checks, and emits fresh attachment digests for comparison. The final encoded MIME message must remain at or below 24 MiB.

The email body does not create a fake link to a MIME attachment. Clients render their own native attachment interface.

### Attachment-description authoring pattern

When a recipient needs context for one or more PDFs, add an ordinary Markdown `## Attachment` or `## Attachments` section. List the exact attachment basename as bold text, followed by one sentence describing its purpose:

```markdown
## Attachment

- **project-brief.pdf**  
  Current scope, decisions, owners, and the next review gate.
```

The filename remains text, not a fake body link. Copy it exactly from the approved attachment manifest and confirm it again during stored-MIME review. This pattern adds no MIME part, attachment metadata field, remote request, or new renderer component. Use it when the filename alone does not explain why the file matters. The validated local fixture is `.pi/fixtures/system-email-surface-v1/attachment-description-message.md`; its preview is `/tmp/system-email-surface-attachment-description-preview.html`.

### PDF preview decision

Automatic PDF previews remain deferred. A generated first-page image would duplicate native attachment UI, increase message weight, introduce a PDF-rendering dependency, require page-selection and derived-image accessibility policy, and create a new binding problem between the preview pixels and the exact reviewed PDF bytes. The current WAWCO use case does not justify that surface.

If a future message needs a visual excerpt from a PDF, supply a deliberately selected opaque PNG through the existing v1.2 or v1.3 figure path and attach the PDF normally. The caption should identify the excerpt and the PDF it accompanies. Treat that as a message-specific figure, not an automatic PDF preview, and retain the existing PNG, alt, caption, attachment-hash, and exact-payload gates.

## Local preview contract

`preview` writes a private mode-0600 HTML file. It refuses an existing output path unless bare `--force` is supplied, and it refuses to follow an output symlink even with `--force`.

The preview includes a restrictive Content Security Policy and no-referrer directive. It renders the generated HTML fragment beside the generated plain-text alternative.

A local preview is structural evidence only. It does not emulate Gmail, Apple Mail, Outlook, mobile clients, dark mode transformations, blocked assets, or provider-side MIME rewriting.

## Approval and send contract

Local preview, dry-run output, and source hashes do not authorize sending.

The send path is:

1. Create a Gmail draft after the intended recipient, subject, body, attachments, and reply context are approved.
2. Review the existing draft immediately before send. Review parses the stored raw MIME and fails closed unless its policy markers, semantic content digest, sender/account match, Noah recipient policy, system note, parser-based HTML attribute/style policy, supported MIME tree, PDF policy, inline-figure binding, attachment limits, and encoded-size limit pass.
3. Confirm the returned recipients, subject, stored MIME structure, content digest, attachment names and SHA-256 values, figure filename/dimensions/alt/caption/SHA-256, and exact raw-MIME SHA-256 token against the approved local summary.
4. Send that draft once with the exact lowercase token. The helper includes the reviewed base64url raw MIME in the same `users.drafts.send` request as the draft ID, using Gmail's documented update-while-sending behavior.
5. Treat any send error as uncertain and check Gmail Sent before another attempt.

The token authorizes only the reviewed Gmail MIME payload. Any payload change invalidates it. The semantic digest and policy markers defend against accidental or manual drift; they do not cryptographically prove helper authorship and are not a substitute for protecting Gmail and service-account credentials.

## Change control

The v1 family presentation baseline is locked for current WAWCO use after Noah approved the revised mobile fixture on 2026-07-24. Profile migration does not itself authorize a visual change. The accepted WAWCO profile must continue resolving to this exact surface until Noah reviews and accepts a new WAWCO profile version. This lock is not a broad cross-client compatibility claim; the incomplete matrix remains explicit.

After lock, a change to supported Markdown, dimensions, type, color, compatibility markup, MIME structure, sanitization, attachment behavior, preview behavior, or approval logic requires:

1. a focused regression test;
2. an updated comprehensive fixture when presentation changes;
3. local verification;
4. renewed named-client evidence when rendering or MIME behavior could change.

A second production visual profile remains deferred. The provisional NEWW profile has no WAWCO-helper account binding or production authority and must pass a separate local shadow-render review before any operational consideration. More than two images, galleries, side-by-side image layouts, rich cards, and PDF previews require separate use cases and compatibility evidence.
